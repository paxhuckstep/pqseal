# pqseal

A small data-sealing service built around the two post-quantum primitives standardized by NIST in August 2024: **ML-KEM-768** (FIPS 203, the standardized form of CRYSTALS-Kyber) for key establishment, and **ML-DSA-65** (FIPS 204, the standardized form of CRYSTALS-Dilithium) for signatures.

## Build and run

```
go mod tidy
go test ./...
go build -o pqseal ./cmd/pqseal
go build -o pqseal-keygen ./cmd/pqseal-keygen

./pqseal-keygen -dir ./testkeys -recipient alice -issuer issuer-1
./pqseal -addr :8443 -keystore ./testkeys
```

The server speaks plain HTTP. There is no TLS, no auth, no logging framework — the spec is explicit that those are out of scope.

## API

`POST /seal`

```json
{
  "recipient_ek_id":  "alice",
  "issuer_priv_id":   "issuer-1",
  "policy":           "clearance >= 'SECRET' AND citizenship == 'USA'",
  "compress":         true,
  "payload_b64":      "SGVsbG8sIFBRIHdvcmxkCg=="
}
```

`POST /unseal`

```json
{
  "envelope_b64":     "UFFTMQ...",
  "recipient_dk_id":  "alice",
  "issuer_pub_id":    "issuer-1",
  "claims": { "clearance": "TOP_SECRET", "citizenship": "USA" }
}
```

Errors are drawn from exactly four buckets:

| Status | Error string             | Cause                                              |
|--------|--------------------------|----------------------------------------------------|
| 400    | `malformed envelope`     | parse / bad magic / bad flags / bad length / oversize |
| 401    | `authentication failed`  | signature OR AEAD failure (collapsed deliberately) |
| 403    | `policy denied`          | claims did not satisfy the policy                  |
| 404    | `unknown key`            | key id not in the keystore                         |

## KEM vs. Diffie-Hellman, in my own words

Diffie-Hellman is symmetric. Each side picks a private scalar, derives a public point, and both sides do the same mixed-key exponentiation to land on a shared secret. Either party can initiate; the shared secret depends equally on both private keys.

A KEM is asymmetric in a different sense. The recipient publishes a long-lived `encapsulation key`, and `Encapsulate(ek)` is a one-sided operation: it samples fresh randomness, derives a 32-byte shared secret `K`, and produces a ciphertext `c` that the sender transmits. The recipient runs `Decapsulate(dk, c)` to recover the same `K`. The sender never holds a keypair — their contribution is the randomness baked into `c`. So in pqseal there is no "sender private key"; the freshness that prevents replays of an entire envelope is delivered by the per-seal randomness inside `EK.Encapsulate()` combined with the fresh AES-GCM nonce. That is also why `c` (the 1088-byte ML-KEM-768 ciphertext) appears on the wire where you would expect an ephemeral public key in an X25519 protocol — same role, different math.

The practical consequence: ML-KEM-768's shared secret is already a 32-byte uniformly random string and can be fed straight into HKDF without the "hash a curve point, watch out for cofactor or zero outputs" gymnastics that X25519 requires.

## Order of operations in `/unseal`

I implemented §8.2 in the order the spec recommends:

1. Parse and structurally validate the envelope.
2. Verify the ML-DSA-65 signature over `SHA-256(envelope[0:end_of_ciphertext])`.
3. Parse the policy from `policy_blob` and evaluate it against the claims.
4. Decapsulate with the recipient ML-KEM-768 decapsulation key.
5. Derive the AES-256 key via HKDF-SHA256.
6. AES-256-GCM open with the policy bytes as additional data.
7. Inflate if the compressed flag is set.

Signature first, policy second, decapsulation last. The reasoning:

- **Signature before policy** so that a tampered `policy_blob` (e.g. an attacker swapping in a more permissive policy) is rejected at step 2 rather than slipping into the policy evaluator. The signature covers the policy bytes; the AAD on the AEAD is a belt-and-suspenders second line.
- **Policy before decapsulation** so that a caller whose claims fail the policy never causes any operation on the recipient's long-term ML-KEM private key. Decapsulation is constant-time and considered safe, but never running it at all on unauthorized requests is a stronger property than running it safely.

Section 8 of the spec notes that swapping steps 3 and 4 still round-trips correctly. We do not swap.

## Constant-time comparisons

The only byte-slice comparisons of secret material in this code happen inside the AEAD (GCM tag check) and inside ML-KEM (implicit-rejection comparison during decapsulation), both of which are already constant-time inside the standard library. There are no user-written `bytes.Equal` calls on derived keys, plaintexts, or shared secrets. Public string ids in the keystore are compared with `==` per the spec note.

## Envelope format

Length-prefixed, big-endian, 16 MiB cap. See [internal/envelope/envelope.go](internal/envelope/envelope.go) for the authoritative field offsets and the `ParseEnvelope` validator. Every length field is bounds-checked against the remaining buffer before any slice is taken, so a hostile length prefix cannot trigger an oversized allocation.

## Key sizes recorded on disk

- `<id>.mlkem.ek`   — **1184 bytes**, ML-KEM-768 encapsulation key (public)
- `<id>.mlkem.dk`   — **64 bytes**, the seed form returned by `(*mlkem.DecapsulationKey768).Bytes()` in Go 1.24+
- `<id>.mldsa.pub`  — **1952 bytes**, ML-DSA-65 public key (CIRCL `MarshalBinary`)
- `<id>.mldsa.priv` — **4032 bytes**, ML-DSA-65 private key (CIRCL `MarshalBinary`)

The keystore loader rejects any public-key file whose size does not match the fixed expected size.

## Tests

`go test ./...` runs:

- Happy-path round-trip with and without compression (`internal/envelope`).
- §9 structural negatives: PQS2 magic, reserved flag bits, bad `kem_ct_len`, bad `sig_len`, `policy_len` overflow, oversized envelope.
- §9 cryptographic negatives: `policy_blob` swap, ciphertext bit-flip detected by signature, ciphertext bit-flip detected by AEAD.
- Property: two seals of the same input produce different envelopes (fresh KEM encap + fresh nonce).
- Policy parser: all worked examples from §6.4, plus precedence, the clearance enumeration, missing-claim handling, the `in` operator, and a battery of parse-error cases.
- HTTP layer: end-to-end seal/unseal via `httptest`, `policy denied`, `unknown key`, ciphertext-tamper, bad magic, invalid policy at seal time.
